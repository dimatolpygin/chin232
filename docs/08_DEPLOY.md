Развёрнут досрочно, на этапе 5: без публичного https вебхук платёжки проверить
нечем. Этап 10 останется на обвязку — бэкапы, мониторинг, автозапуск обновлений.

## Как выкатить изменения

Репозиторий на GitHub пустой, код уезжает с машины разработки архивом:

```bash
git archive --format=tar HEAD -o /tmp/china.tar
pscp /tmp/china.tar root@104.143.218.104:/root/
ssh root@104.143.218.104
cd /opt/china_bot && tar -xf /root/china.tar && rm /root/china.tar
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Миграции накатываются сами при старте `china_bot`, отдельной команды не нужно.

`.env` на сервере свой и в архив не попадает: пароль базы и секрет вебхука там
сгенерированы отдельно от машины разработки. При распаковке архива он не
затирается, но проверять после каждого деплоя стоит.

## Грабли, на которые уже наступили

**CRLF в `entrypoint.sh`.** Разработка на Windows, скрипт уехал с CRLF, и все
три контейнера падали в цикле с `exec docker/entrypoint.sh failed: Permission
denied` — tini не находит интерпретатор из-за `\r` в шебанге. Лечится
`.gitattributes` с `*.sh text eol=lf`, он в репозитории.

**Dev-монтирования уезжали в прод.** Прод-оверрайд глушил их пустым
`volumes: []` — так это не работает: пустой список ничего не отменяет, compose
оставлял бинды из базового файла. На сервер уезжал код с хоста, а вместе с ним
`entrypoint.sh` без бита запуска, и контейнеры снова падали с Permission denied.
Починено разделением: dev-монтирования переехали в `docker-compose.override.yml`
(compose подхватывает его сам локально и не подхватывает при боевой команде с
двумя явными `-f`), а сам `entrypoint.sh` теперь лежит в репозитории с правами
`100755`.

**Один токен на два процесса.** Telegram не отдаёт апдейты двум поллерам сразу.
Пока бот работает на сервере, локальный контейнер `china_bot` должен быть
погашен, иначе оба валятся с 409. Для параллельной разработки нужен отдельный
тестовый бот у @BotFather.

## Проверка живости

```bash
curl https://chinesetonebot.ru/health
docker ps --format '{{.Names}}\t{{.Status}}'
docker logs china_bot --tail 20
```

Вебхук отвечает `401` на чужой ключ и `200` на верный — быстрый способ убедиться,
что Caddy проксирует, а секрет в `.env` совпадает с кабинетом платёжки.

## Автовыкатка через GitHub Actions

Джоба `deploy` в `.github/workflows/ci.yml` срабатывает на пуш в `main` и только
после зелёных `lint-and-test` и `secrets-check`. Она заходит на сервер по ssh
отдельным ключом, делает `git reset --hard origin/main`, пересобирает образ,
поднимает контейнеры и ждёт зелёного `/health`. Если здоровье не поднялось за
сто секунд, джоба падает — молчаливой выкатки сломанного бота не будет.

`.env` на сервере автовыкатка не трогает: он в `.gitignore`, `git reset --hard`
его не видит. Миграции накатывает `entrypoint.sh` при старте контейнера.

Ключ доступа отдельный, ed25519, создан только для выкатки: приватная часть
лежит в `.secrets/deploy_key` (каталог в `.gitignore`), публичная — в
`/root/.ssh/authorized_keys` на сервере. Личный пароль root в Actions не
передаётся.

Секреты репозитория (Settings → Secrets and variables → Actions):

| Имя | Что кладём |
|---|---|
| `SERVER_HOST` | адрес сервера |
| `SERVER_USER` | `root` |
| `SSH_PRIVATE_KEY` | приватный ключ выкатки целиком, вместе со строками BEGIN и END |
| `SERVER_HOST_KEY` | строка known_hosts с отпечатком сервера |

Секреты заведены 20.08.2026, `/opt/china_bot` превращён в клон репозитория,
пайплайн прогнан вживую до зелёного: пуш в `main` собрал, прогнал тесты,
выкатил и дождался `/health`. Ручная выкатка архивом больше не нужна, она
остаётся только на случай, когда GitHub недоступен.

Ещё одни грабли оттуда же: в шагах workflow имена переменных только латиницей.
bash на раннере падает на кириллическом идентификаторе с `not a valid
identifier`, и джоба помечает успешную выкатку как провал.

## Бэкапы и логи

Дамп базы каждую ночь в 03:30 через `/etc/cron.d/china_backup`, скрипт
`/opt/backup/pg_dump.sh`, файлы `china_bot-ГГГГ-ММ-ДД.sql.gz` в `/opt/backup`.
Хранится неделя, дальше затирается, отчёт дописывается в `/opt/backup/backup.log`.

Восстановление:

```bash
gunzip -c /opt/backup/china_bot-2026-08-20.sql.gz | \
  docker exec -i china_postgres psql -U china_bot -d china_bot
```

Дампы лежат на том же диске, что и база: от потери сервера они не спасают.
Поэтому поверх них работает второй уровень — копия в стороннем хранилище.

### Копия в S3

Каждую ночь в 03:30 по Москве задача воркера `backup_database` снимает дамп
через `pg_dump`, сжимает и кладёт в S3-хранилище Beget. Расписание — в
`WorkerSettings.cron_jobs`, время там UTC, поэтому в коде стоит 00:30.

| Что | Значение |
|---|---|
| Хранилище | `https://s3.ru1.storage.beget.cloud`, регион `ru1` |
| Бакет | `bbd5f068f995-n8n` — **общий с проектом n8n** |
| Папка | `a_clients_project_2026/china_bot_backaps/` |
| Имя файла | `china_bot-ГГГГ-ММ-ДД.sql.gz` |
| Ключи | `S3_*` в `.env` сервера, они же в `dostupi.txt` |

Хранится 7 последних дней подряд плюс 4 воскресенья в глубину — это ответ и на
«вчера всё работало», и на «когда именно данные испортились», ценой примерно
десяти файлов. Дамп этой базы весит единицы мегабайт, так что всё хранение —
десятки мегабайт, а не гигабайты. Глубина правится переменными
`BACKUP_KEEP_DAILY` и `BACKUP_KEEP_WEEKLY`.

Уборка старого работает **только внутри своего префикса и только по своему
шаблону имени**: бакет общий, и чужой файл не удаляется ни при какой настройке.
Порядок в задаче тоже не случайный — сначала кладём новую копию, потом убираем
старые, иначе упавшая загрузка оставила бы проект вообще без копий.

Клиент S3 свой, на httpx с подписью AWS SigV4 (`app/core/providers/storage/`).
boto3 не поставили намеренно: ради четырёх запросов он добавил бы к образу
под сотню мегабайт, а образ собирается на одном ядре.

В образ добавлен `postgresql-client` — им и снимается дамп. Штатного клиента
debian хватает: база у нас 16, а в базовом образе `python:3.12-slim` (сейчас
trixie) лежит 17, и клиент новее сервера дампит нормально. Наоборот нельзя,
поэтому в Dockerfile стоит проверка версии прямо при сборке — первая попытка
с репозиторием PGDG для bookworm как раз и сломалась о то, что базовый образ
успел переехать на trixie.

Если копия не собралась — бот пишет об этом всем админам в телеграм. Бэкап, о
поломке которого никто не знает, — это не бэкап.

### Восстановление из S3

```bash
cd /opt/china_bot
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec -e PYTHONPATH=/app worker python -m app.tools.s3backup список

docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  exec -e PYTHONPATH=/app worker \
  python -m app.tools.s3backup восстановить china_bot-2026-08-24.sql.gz --да
```

Без `--да` команда ничего не делает и предупреждает, что затрёт живую базу.
Есть ещё `снять` (внеплановая копия перед рискованной операцией) и `скачать`.

**Чего в копии нет и где это взять.** В хранилище уезжает только база. `.env`
с боевого сервера туда не кладётся намеренно — там пароль базы, токен бота,
ключи сервисов и секрет вебхука, а бакет общий с чужим проектом; все эти
значения лежат в `dostupi.txt` и восстанавливаются руками. Redis не бэкапится
вовсе: это очередь и кеш, в худшем случае теряются круги, которые были в
работе в момент падения.

Порядок переезда на новый сервер: поднять docker и склонировать репозиторий,
положить `.env` из `dostupi.txt`, поднять контейнеры, дождаться миграций,
накатить последнюю копию командой выше, перезапустить бота и воркер.

### Логи
Логи Docker ограничены в `/etc/docker/daemon.json`: 20 МБ на файл, 5 файлов на
контейнер. Без этого json-file пишет без предела и однажды забивает диск.

## Восстановление с нуля

Проверка на честность: если сервера завтра не станет, из чего поднимается бот?

| Что | Где лежит | Кто отвечает |
|---|---|---|
| Код | GitHub, `dimatolpygin/chin232` | репозиторий |
| Настройка хоста: docker, swap, лимиты логов, Caddy, ночной дамп | `deploy/` в репозитории, ставится `deploy/bootstrap.sh` | репозиторий |
| Данные (юзеры, подписки, диалоги, платежи) | S3, ночная копия | хранилище |
| Секреты: токен бота, ключи сервисов, пароль базы, секрет вебхука | `.env` на сервере и `dostupi.txt` на машине разработки | **только человек** |
| Домен и A-запись | reg.ru | человек |
| Ключ автовыкатки | `.secrets/deploy_key`, публичная часть в `authorized_keys` | человек |

Redis не восстанавливается сознательно: там очередь и кеш, в худшем случае
теряются круги, которые шли в момент падения.

Порядок на чистой Ubuntu 24.04:

```bash
git clone https://github.com/dimatolpygin/chin232 /opt/china_bot
cd /opt/china_bot && bash deploy/bootstrap.sh     # docker, swap, Caddy, cron
# положить .env из dostupi.txt, направить A-запись домена на новый IP
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml   exec -e PYTHONPATH=/app worker python -m app.tools.s3backup список
docker compose -f docker-compose.yml -f docker-compose.prod.yml   exec -e PYTHONPATH=/app worker   python -m app.tools.s3backup восстановить ИМЯ_ФАЙЛА --да
curl https://chinesetonebot.ru/health
```

`bootstrap.sh` идемпотентный: повторный запуск ничего не ломает. Базу он не
трогает и `.env` не создаёт — секреты кладутся руками.

**Единственное слабое место — `.env`.** Он не в репозитории (и не должен там
быть) и не в хранилище (бакет общий с чужим проектом). Копия одна: `dostupi.txt`
на машине разработки. Если пропадёт и она, восстановимо всё, кроме двух вещей:
секрет вебхука lava.top придётся задать заново в кабинете, а пароль базы —
сгенерировать новый (данные от этого не теряются, они в дампе). Токен бота
берётся у @BotFather, ключи сервисов — в их кабинетах.

### Проверка копии восстановлением

Копия, из которой ни разу не поднимались, — это надежда, а не копия. Поэтому
по воскресеньям в 04:30 МСК задача `verify_backup` берёт свежий файл из
хранилища, наливает его в отдельную базу `china_bot_verify`, считает таблицы и
удаляет её. Не получилось — админам приходит сообщение.

Руками то же самое:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml   exec -e PYTHONPATH=/app worker python -m app.tools.s3backup проверить
```

Проверка эта не формальность: именно она поймала первую версию бэкапа. Дамп
снимался клиентом 17, а сервер у нас 16 — pg_dump писал в заголовок
`SET transaction_timeout`, которого шестнадцатый не знает, и файл не
накатывался никуда. Со стороны всё выглядело идеально: копии есть, размер
правильный, ошибок нет. Поэтому версия клиента в `docker/Dockerfile` теперь
прибита к версии сервера и проверяется при сборке.

## Нагрузка: когда менять сервер

Машина одноядерная, и упирается она не во внешние сервисы, а в свой процессор:
единственный кусок круга, который считаем мы сами, — конвертация звука через
ffmpeg. На живой проверке двадцать одновременных кругов дали медиану 9.7 с при
одиночном круге в 2.5 с — то есть запаса по ядру практически нет.

Чтобы это не выяснялось от пользователей, каждый круг пишет событие
`round_timing`: сколько реплика пролежала в очереди, сколько считался сам круг
и сколько из него занял ffmpeg. По ним считается сводка (`/admin` → Нагрузка) с
приговором в трёх состояниях:

| Приговор | Когда | Что делать |
|---|---|---|
| запас есть | ожидание очереди в худших 5% меньше 1.5 с, медленных кругов меньше 5% | ничего |
| плотно | ожидание 1.5–5 с, или медленных 5–20%, или загрузка ядра выше 1 | планировать переезд на тариф мощнее |
| потолок | ожидание больше 5 с, или медленных больше 20%, или загрузка ядра выше 2 | добавлять ядра |

Первым растёт именно **ожидание в очереди** — раньше, чем длительность самого
круга, поэтому оно и взято главным признаком. Доля ffmpeg на экране отвечает
на другой вопрос: если тормозит не она, а чужой сервер, то новые ядра денег
стоят, а времени не вернут.

Раз в час задача `watch_load` считает то же самое за последние 6 часов, и при
приговоре «потолок» бот сам пишет админам — не чаще раза в сутки, иначе на эти
сообщения перестанут смотреть.
