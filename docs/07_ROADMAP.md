# Дорожная карта реализации

11 этапов от пустого репозитория до прод-готовности. Каждый этап заканчивается
**демонстрируемым результатом**, который можно потрогать руками в боте.

Ключевая идея: MVP-first. Этап 1 это тонкая, но живая вертикаль — юзер уже
говорит с ботом голосом. Всё остальное наслаивается без перепиливания базы.

> **Где смотреть прогресс**: [`STATUS.md`](STATUS.md). Внутри каждого этапа ниже
> чекбоксы конкретных acceptance-пунктов. Закрытие этапа сопровождается
> git-тегом `stage-N-done` и только после живой проверки человеком.

| # | Этап | Главный артефакт | Зависит от |
|---|---|---|---|
| 0 | Каркас | контейнер поднимается, бот отвечает на /start, миграции накатились | — |
| 1 | Голосовой круг | сказал голосом, получил голосовой ответ на китайском | 0 |
| 2 | Текст и подсказки | кнопки «Текст» и «Помощь» под ответом | 1 |
| 3 | Оценка произношения | баллы по тонам на каждый иероглиф | 1 |
| 4 | Лимиты | счётчик под ответом, стена при исчерпании | 1 |
| 5 | Подписка и оплата | оплатил через LavaTop, лимит снялся | 4 |
| 6 | Настройки | смена уровня, голоса, скорости, темы | 1 |
| 7 | Прогресс | стрик и календарь практики | 1 |
| 8 | Админка | лимиты и цена меняются без деплоя | 4, 5 |
| 9 | Полировка | тексты, ошибки, крайние случаи, нагрузка | 2-8 |
| 10 | Деплой | бот работает на сервере клиента, CI/CD настроен | 9 |

## Этап 0 — Каркас

**Цель**: пустой, но полностью рабочий проект, в котором есть всё для следующих
этапов. Дальше ни разу не придётся возвращаться и «доставлять инфраструктуру».

**Что делаем**: структуру папок из ТЗ, docker compose с dev и prod режимами,
конфиг на pydantic-settings, structlog, подключение к postgres и redis, Alembic
с автонакатом, первые модели (`users`, `identities`, `events`, `settings`),
функцию `track()`, health-эндпоинт FastAPI, воркер arq, заготовку CI, `.env.example`.

**Критерии приёмки**:

- [x] `docker compose up` поднимает бота, воркер и API без ручных действий
- [x] при старте автоматически прогоняется `alembic upgrade head`, в логах видно, какие ревизии накатились
- [x] в базе `china_bot` появились таблицы `users`, `identities`, `events`, `settings`, `alembic_version`
- [x] база и пользователь `china_bot` отдельные, чужие базы в postgres16 не затронуты
- [x] `/start` в боте отвечает заглушкой, в базе создаётся запись в `users` и `identities`
- [x] правка любого `.py` перезапускает процесс без пересборки образа
- [x] в логах видно: дата, username, user_id, first_name, текст входящего и текст ответа, всё на русском
- [x] в логах есть `request_id`, по нему одна реплика собирается в цепочку
- [x] отсутствие обязательной переменной окружения роняет старт с внятным сообщением
- [x] `GET /health` отвечает 200 и показывает состояние postgres и redis
- [x] `git check-ignore dostupi.txt` подтверждает, что доступы вне git
- [x] `git grep --cached` не находит ни одного ключа в индексе

(закрытие → tag `stage-0-done`)

## Этап 1 — Голосовой круг

**Цель**: живая вертикаль. Пользователь говорит голосом и получает голосовой
ответ на китайском. Это уже продукт, пусть и голый.

**Что делаем**: провайдеров STT, LLM, TTS за интерфейсами, ffmpeg-конвертацию,
обработку круга в очереди arq, выбор уровня HSK на входе, промпты в базе,
сохранение реплик в `dialogs`.

**Критерии приёмки**:

- [x] `/start` показывает приветствие и кнопки выбора уровня HSK
- [x] после выбора уровня бот сразу присылает первую фразу голосом, меню не требуется
- [x] голосовое от юзера распознаётся, распознанный текст виден в логах
- [x] бот отвечает **голосовым сообщением**, а не файлом (ogg/opus, видна волна)
- [x] вместе с голосовым приходит тот же текст иероглифами
- [x] бот понимает запрос на русском и отвечает по-китайски
- [x] бот понимает запрос на китайском
- [x] ответ на уровне HSK 1-2 заметно проще, чем на HSK 5-6 (проверяется сменой уровня в базе)
- [x] круг без скачивания голосового укладывается в 12 секунд на обычной реплике
      (замер: 7-8 сек. Скачивание из Telegram добавляет 2-8 сек и зависит от
      канала машины — на медленном локальном интернете разработчика итог доходил
      до 14 сек. Итоговое время перепроверяется на сервере, этап 10)
- [x] круг выполняется в воркере, бот в это время не блокируется на других юзерах
- [x] сбой любого внешнего сервиса не роняет бота: юзер видит понятное сообщение, ошибка с телом ответа в логах
- [x] каждый вызов внешнего сервиса залогирован: провайдер, длительность, объём, http-код
- [x] реплики юзера и бота сохраняются в `dialogs`
- [x] смена `TTS_PROVIDER` в окружении не требует правок кода

(закрытие → tag `stage-1-done`)

## Этап 2 — Текст и подсказки

**Цель**: ученик может разобрать то, что не понял на слух.

**Что делаем**: кнопки «Текст» и «Помощь» под каждым ответом, структурированный
ответ LLM (иероглифы, пиньинь, перевод, варианты ответа), мягкое исправление
ошибок отдельным блоком.

**Критерии приёмки**:

- [x] под каждым голосовым ответом бота видны кнопки «Текст» и «Помощь»
- [x] «Текст» показывает пиньинь **со знаками тонов** и перевод на русский
- [x] «Текст» не делает новых платных вызовов, данные берутся из уже сохранённого
      (подтверждено логами: в момент нажатия воркер молчит, `пиньинь_локально=False`)
- [x] «Помощь» даёт 2-3 варианта ответа на китайском с переводом каждого
- [x] варианты соответствуют уровню HSK пользователя
- [x] если юзер ошибся, бот присылает исправление отдельным текстовым блоком, не ломая голосовой поток
- [x] исправление объясняет, что именно не так, а не просто даёт верную фразу
      (проверено прогоном боевого промпта из базы на трёх ошибках: счётное слово
      本/个, 是 против 人, лишнее 了 — во всех случаях названо правило)
- [x] повторное нажатие кнопки не дублирует сообщения
      (основной механизм — нажатая кнопка исчезает — проверен вживую; замок в
      Redis на двойной тап во время работы живьём не срабатывал ни разу)

(закрытие → tag `stage-2-done`)

## Этап 3 — Оценка произношения

**Цель**: главная фича тарифа. Балл по тонам на каждый иероглиф.

**Что делаем**: провайдер SpeechSuper, подписи SHA1, конвертация в WAV 16 кГц,
механику «повтори за мной», разбор и отрисовку результата, сохранение полного JSON.

**Критерии приёмки**:

- [x] под ответом бота есть кнопка «Оценка»
- [x] нажатие показывает эталонную фразу и озвучивает её
- [x] эталоном берётся последняя фраза бота, а при наличии ошибки у юзера — исправленный
      вариант его фразы (реплика 46: сказано `我用算计数`, эталоном пришло `我在算数`)
- [x] после записи голосового приходит общий балл и балл на каждый иероглиф
- [x] сбитые тоны отмечены визуально, видно, где именно ошибка (красная строка и балл
      тона на иероглиф; услышанный тон даёт только тариф promax, его на ключе нет)
- [x] показан пиньинь со знаками тонов
- [x] намеренно неправильно произнесённый тон роняет балл этого иероглифа (оценка 6:
      你 — звуки 100, тон 25, против сплошных сотен в оценке 5 на той же фразе)
- [x] кнопки «Послушать эталон» и «Попробовать ещё раз» работают
- [x] полный JSON ответа сервиса сохраняется в `pronunciation_checks.detail`
- [x] шумная или пустая запись даёт понятное сообщение, а не молчание или трейс (нули
      по всей фразе; неполная фраза получает разбор и отдельную подсказку)

(закрытие → tag `stage-3-done`)

## Этап 4 — Лимиты

**Цель**: бесплатный доступ ограничен, стена мотивирует к подписке.

**Что делаем**: счётчики в Redis с TTL до полуночи по Москве, дублирование в
`daily_usage`, отдельный лимит на разборы, пробный период 3 дня, все числа в базе.

**Критерии приёмки**:

- [x] под ответом видна строка «осталось N из M на сегодня» (в пробном периоде с подписью «пробный период»)
- [x] счётчик уменьшается на каждое голосовое (и на текстовую реплику: круг и цена у них те же)
- [x] разборы произношения считаются **отдельным** счётчиком
- [x] первые 3 дня после регистрации лимит повышенный (30), потом обычный (10)
- [x] при исчерпании бот показывает экран с кнопками «Оформить подписку» и «Напомнить завтра»
- [x] после исчерпания сообщения юзера не обрабатываются и **платные сервисы не вызываются** (проверено по логам воркера; общая стена закрывает и разбор произношения)
- [x] в полночь по Москве счётчик обнуляется (TTL ключа redis, замерен: 43 985 с до 00:00 МСК)
- [x] лимиты берутся из базы, изменение значения меняет поведение без перезапуска (проверено правкой settings['limits'] на живом боте)
- [x] расход дублируется в `daily_usage` для истории

(закрытие → tag `stage-4-done`)

## Этап 5 — Подписка и оплата

**Цель**: деньги. Юзер платит и получает безлимит.

**Что делаем**: таблицы `plans`, `subscriptions`, `payments`, интеграцию LavaTop,
вебхук на FastAPI с проверкой подписи и идемпотентностью, раздел «Подписка».

**Критерии приёмки**:

- [ ] раздел «Подписка» показывает цену и что даёт подписка
- [ ] кнопка «Оформить» ведёт на оплату LavaTop
- [ ] оплата картой проходит до конца и возвращает юзера в бот
- [ ] оплата через СБП проходит до конца
- [ ] после оплаты подписка активна, лимиты сняты, юзер видит подтверждение в боте
- [ ] запись появляется в `payments` и `subscriptions`, статусы верные
- [ ] **повторно присланный вебхук не продлевает подписку дважды** (проверяется ручной отправкой)
- [ ] вебхук с неверной подписью отклоняется и логируется
- [ ] у платного юзера раздел показывает «активна до <дата>»
- [ ] по истечении срока подписка становится expired, лимиты возвращаются
- [ ] каждое движение денег залогировано

(закрытие → tag `stage-5-done`)

## Этап 6 — Настройки

**Цель**: юзер настраивает бота под себя.

**Критерии приёмки**:

- [ ] раздел «Настройки» открывается из нижнего меню
- [ ] смена уровня HSK меняет сложность следующих ответов
- [ ] список голосов, у каждого кнопка «Прослушать», приходит образец
- [ ] выбранный голос применяется к следующим ответам
- [ ] скорость (медленно, обычно, быстро) слышимо меняет темп речи
- [ ] выбор темы меняет направление разговора, бот сам начинает по теме
- [ ] все настройки сохраняются в `users` и переживают перезапуск бота
- [ ] голоса в списке нейтральные и дикторские, без клонов публичных людей

(закрытие → tag `stage-6-done`)

## Этап 8 — Админка

**Цель**: клиент управляет ботом сам, без разработчика.

**Критерии приёмки**:

- [ ] `/admin` доступен только id из конфига, остальным не отвечает
- [ ] лимиты сообщений и разборов меняются из админки и **сразу** влияют на юзеров
- [ ] длина пробного периода меняется из админки
- [ ] цена подписки меняется из админки
- [ ] статистика показывает: всего юзеров, активных за день и неделю, платящих, конверсию
- [ ] видно расход по каждому внешнему сервису
- [ ] рассылка отправляется всем или сегменту, с отчётом о доставке
- [ ] рассылка не блокирует бота и уважает лимиты Telegram

(закрытие → tag `stage-8-done`)

## Этап 9 — Полировка

**Цель**: бот не разваливается в руках живого человека.

**Критерии приёмки**:

- [ ] тексты интерфейса вычитаны, единый тон, без технических терминов
- [ ] отправка не-голосового и не-текстового (фото, стикер, документ) обрабатывается понятно
- [ ] очень длинное голосовое обрезается или отклоняется с объяснением
- [ ] молчаливое или пустое голосовое не роняет круг
- [ ] недоступность каждого из четырёх внешних сервисов проверена искусственно, юзер всегда видит понятное сообщение
- [ ] повторные быстрые нажатия кнопок не создают дублей
- [ ] 20 одновременных диалогов обрабатываются без деградации
- [ ] перезапуск контейнера не теряет незавершённые задачи очереди
- [ ] в логах нет секретов, проверено грепом
- [ ] тесты проходят, линт чистый

(закрытие → tag `stage-9-done`)

## Этап 10 — Деплой

**Цель**: бот живёт на сервере клиента, обновляется пушем в main.

**Что делаем**: по навыку `/okdeploy`.

**Критерии приёмки**:

- [ ] сервер подготовлен: docker, git, swap, firewall
- [ ] бот работает на сервере, а не на машине разработки
- [ ] `.env` на сервере, в репозиторий не попал
- [ ] push в `main` автоматически прогоняет линт и тесты
- [ ] после успешного CI изменения выкатываются на сервер сами
- [ ] миграции накатываются при деплое автоматически
- [ ] `/health` отвечает 200 после выката
- [ ] бот переживает перезагрузку сервера и поднимается сам
- [ ] логи пишутся в файл с ротацией, старые не съедают диск
- [ ] есть бэкап базы по расписанию
- [ ] проверен откат на предыдущую версию
- [ ] полный круг с голосовым укладывается в 12 секунд на канале сервера
      (перенесено с этапа 1: локально мешал медленный интернет разработчика)
- [ ] клиент получил исходный код и доступ к репозиторию

(закрытие → tag `stage-10-done`)
